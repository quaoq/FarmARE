# Exact scenario and confirmation wiring

This change repairs release mechanics. It does **not** select or release a drought
candidate, pass a confirmation gate, or provide professor approval. The latest
`drought_pulse_v4` development screen still passes four of five pairs; world 0
does not complete harvest. No new simulator cohort or model call was used here.

## What is executable now

Matrices accept one explicit native configuration per scenario, shared across
all assigned conditions:

```yaml
native_scenario_by_id:
  farm_disease_drought:
    scenario_revision: drought_pulse_v4
    calibration_candidate: true
```

This selects the already documented 0.4 m root layer, 38-day drought forcing,
five-hour/25 mm reference irrigation and 9.375 field-mm quota. It does not alter
rewards, thresholds, or other management limits. The setting reaches distributed
execution, direct/A2A baselines, specification compilation and native preflight.
Variant assignments have distinct run, pair and world-cluster identities from
the historical scenario. A loaded specification must declare matching native
settings; a historical specification cannot silently score the larger dose.

`drought_pulse_v4.process.json` is an **unreleased development specification**
generated by `author_process("farm_disease_drought",
scenario_revision="drought_pulse_v4", calibration_candidate=True)`. Its irrigation
acceptance requires exactly five hours. The 13 primary/sensitivity/team artifacts
remain on the historical scenarios; this candidate is not substituted into them.

## Confirmation versus study worlds

The optional gate field `scenario_confirmation` uses the strict
`DroughtConfirmationBinding` schema. It records:

- Exact scenario revision and weather variant; the reference retry days and
  eligible rejection types. Reference retries do not automatically act for agents.
- Process, protocol and executable-source SHA-256 digests.
- Disjoint development, confirmation, live-smoke and study cohorts. Current
  reservations remain 0–9, 20–24, 30–31 and 100–109 respectively.
- At least five complete confirmation pairs and unchanged minimum thresholds:
  50% target root stress and 1% omission loss in every pair.

Save this design **before** confirmation and provide it with
`calibrate-scenario --confirmation-manifest <design.json>`. The command rejects
different cohorts, physics settings, dose revisions or reference retry policies
before creating output. Calibration without a design is limited to worlds 0–9.
The report embeds the exact design and records whether executable source changed
during measurement. Release validation recomputes every pair and verifies the
design, source and protocol. Missing, inactive, incomplete or null-effect pairs
remain failures. Study worlds must belong to the frozen study cohort; they need
not appear in confirmation measurements. No design or sign-off has been fabricated.

Historical sensitivity reports retain the same-world/default-scenario route;
both routes enforce the minimum screening thresholds. Development reports cannot
be relabelled confirmation or used to authorize a different native scenario.
Runtime, doctor and handoff use the same gate verifier. Direct and A2A paper
baselines now invoke the distributed runtime's scientific gate before providers.

Preflight checks use v5 treatment modes and frozen phase/route/send-order selectors,
not scripted message names. They report reference-trace target availability;
actual injector activation remains a separate integration/live-run measurement.
No qualifying handoff is retained and does not invalidate treatment assignment.

## Remaining scientific boundary

The failed development world first rejects target harvest for immaturity/rain;
grain-moisture rejection is recorded from wait day 13 onward. At the fixed
21-day cap, target grain is still above the native 18% limit. This is not repaired
by changing yield reporting or claiming the partial harvest as a final outcome.
A justified, versioned scenario/reference-workflow decision remains necessary
before freezing confirmation. No additional dose search, harvest-cap extension,
confirmation run or study launch is part of this implementation change.

Regression evidence is recorded in `../handover_validation/` and the preserved
raw verification directory under `results/aamas_handover/release_wiring_validation/`.
Synthetic unit-test pairs are software fixtures, never scientific evidence.
